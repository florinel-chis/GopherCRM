> **Baseline audit:** 2026-08-05; historical suite totals below have not been recounted.
> **Purpose:** Track all user-facing features, their test coverage, known gaps, and issues.
> **Convention:** Each feature is described from the user's perspective. Backend and frontend are on the same row.

The baseline rows were checked against the code and tests during the original audit;
later additions identify their own coverage. Where a claim
could not be established from the code it is marked **unverified** rather than guessed. Test counts
are mechanical: Playwright `test(...)` calls; Go test cases (top-level `func Test*` for plain files,
testify suite `Test*` methods for suite files — the one-line suite runner is not counted); and
Vitest `it(...)`/`test(...)` calls. Go subtests inside a `t.Run` are noted where they carry the
coverage.

## Continuous integration

[CI](../.github/workflows/ci.yml) runs on pull requests, merge-queue groups and pushes to `main`.
Application changes run repository hygiene; Go build, vet and race tests; frontend build,
lint and unit tests; and selected Playwright specs on MySQL 8, MariaDB 10.11 and SQLite.
PRs select health smoke and affected feature specs, with full coverage for shared or unmapped
application changes. Runner-only changes use hygiene, runner/probe tests, API/frontend build
health checks and browser health smoke. The bounded auth profile uses auth/session race tests,
API/frontend builds and health/login/registration browsers. The auth-persistence profile adds
real SQLite/MySQL rotation and transaction boundaries, migrations and auth browsers, with
additional MariaDB coverage in CI. It requires all six rotation boundary roots at the candidate;
shared-interface edits also need proof that only the refresh-token interface body changed.
The bounded mailer profile uses SMTP deadline/header/TLS/privacy race tests, focused
password-reset/form/quote/automation delivery callers, API/frontend builds and health smoke; no full frontend
unit suite or unrelated feature browser is selected. Missing or skipped required roots fail.
It changes no database behavior; the existing migration gates and all-engine CI health remain.
Other shared repository/schema/mixed changes retain full fallback. The bounded transaction-helper profile uses API build/vet, transaction
and caller race regressions, configured migration checks and browser health smoke, with
SQLite/MySQL locally and additional MariaDB boundaries in CI. The existing empty lead-conversion
concurrency placeholder remains a reported gap. `make verify` runs the complete non-browser checks
locally; unfiltered `make e2e` runs the full browser suite. The manual
[Release workflow](../.github/workflows/release.yml) always runs full validation before tagging
and publishing verified artifacts. Production deploys consume those published artifacts.
The bounded migration-workflow profile runs SQL/SQLite migration checks and health smoke; its
two database CI jobs feed the existing required Backend check. See the [validation and release runbook](VALIDATION_RELEASE.md).
The separate [Database migrations workflow](../.github/workflows/migrations.yml) runs fresh,
populated-upgrade and rollback/reapply SQL regressions on MySQL 8 and MariaDB 10.11, alongside
the SQLite upgrade fixtures, on every PR, merge group and main push. Required roots and their
descendants cannot be skipped; revision-bound JSON artifacts retain the results.
CI also publishes documentation impact. New local workflow configurations require explicit
documentation review and verify reviewed document contents after merge; see
[documentation maintenance](DOCUMENTATION_WORKFLOW.md). The CI impact report alone is not
an approval of documentation accuracy.

## How to Read This Document

| Column | Meaning |
|--------|---------|
| **Feature** | What the user can do |
| **Description** | How it works end-to-end |
| **E2E Tests** | Playwright tests that exercise the full stack |
| **Unit Tests** | Go handler/service tests + frontend component tests |
| **Integration Tests** | Go tests that hit a real database (SQLite in-memory) |
| **Status** | `covered` / `partial` / `gap` / `untested` / `unverified` |
| **Known Issues** | Bugs, limitations, missing scenarios |

Status meanings:
- **covered** -- happy path and key edge cases are tested
- **partial** -- happy path tested, but significant scenarios missing
- **gap** -- feature exists but important test coverage is missing
- **untested** -- no automated tests exist
- **unverified** -- the row could not be confirmed from the code; treat the status as unknown

## 4d. Products & Quotes (2026-10)

A product catalogue (name, SKU, integer price in minor units next to an ISO 4217 code, active
flag) and quotes that belong to a customer and/or a deal. A quote has lines (a product, a quantity
and a per-line discount in basis points); the line copies the product's name and price when it is
added, and the line and quote totals are computed on the server with round-half-up. Every quote
moves through `draft → sent → accepted | rejected | expired`, with `sent → draft` to revise; each
move is claimed by a conditional update and writes a status-history row in the same transaction,
and only a draft is editable. Quotes use the deal role guard (admin and sales; sales sees only the
quotes it owns, narrowed inside the query). A sent or accepted quote can be emailed as a plaintext
rendering (not the printable document, and not a PDF) to the linked customer's current address
with a fixed subject; the mailer refuses CR/LF in headers. Quotes copy no personal data, so the
erasure cascade and the PII sweep stay correct. Decided for this release: accepting a quote does
not change its deal; expiry is manual (acceptance is refused after `valid_until`); support cannot
read quotes; sending is refused when the quote has no live customer. The frontend slice (4d.9,
2026-10-28, issue #167) adds the `/products` list and admin-only form, the `/quotes` list with its
create dialog, the `/quotes/{id}` detail with draft-only line editing, the valid-transition status
buttons, the email confirmation and the status history, the `/quotes/{id}/print` print layout,
the DealDetail "Quotes" section and the admin/sales-only navigation entries and routes. Money is
shown from the server's integer minor units with the quote's currency, discounts are typed as
percentages and sent as basis points, and the totals are always the server's. Catalog cases in
`docs/testing/15-products-quotes.md`; API contract in `api/swagger.yaml` under `/products` and
`/quotes`.

## 4e. Follow-up Automation & Notifications (2026-10)

Admin-defined rules start on lead events, deal events or a daily UTC schedule and run ordered
steps (`wait`, `condition`, `create_task`, `assign_owner`, `send_email` to a staff user, `notify`)
as persisted runs. Every lead and deal write records an outbox event in the transaction that
commits it; a single-replica worker turns events into runs, executes each step behind a locking
read of the record and a conditional advance of the run row, parks waits in `resume_at`, continues
schedule passes from a persisted cursor and reconciles interrupted runs at boot. A dry run reports
each step's would-be outcome and writes, sends and notifies nothing. Rules are admin-only; the run
history follows lead and deal visibility; notifications are the recipient's own. The screens
(rule list, form and dry run, run list and detail, the Automation sections on leads and deals, the
notification bell and page) shipped on 2026-10-29 (4e.17); captures in
[SCREENSHOTS.md](SCREENSHOTS.md#follow-up-automation). Catalog
cases in `docs/testing/16-follow-up-automation.md`; runtime design in
[DEVELOPMENT.md](DEVELOPMENT.md#automation-runtime); tables in [datamodel.md](datamodel.md#follow-up-automation).
