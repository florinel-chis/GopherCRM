## Continuous integration

[CI](../.github/workflows/ci.yml) runs on pull requests, merge-queue groups and pushes to `main`.
Outside a release they run repository hygiene; a Go build and vet of the module, the API reference
check and `go test -count=1` (no race detector) on the changed packages, their importers and the
packages that read the changed files (`scripts/ci/check-changed-go.py`), repeated against MariaDB
10.11 in the database gates job; and `make verify-frontend`: the frontend build, the end-to-end
type-check (`tsc -p tsconfig.e2e.json`), lint and unit tests. A documentation-only change runs no
Go test. A pull request that changes migration code also runs `Migrations (MySQL 8)`.
The race suite, the two-engine migrations matrix and Playwright on MySQL 8, MariaDB 10.11
and SQLite run only for a release (a manual CI run with `full: true` runs all but the browsers).
The profiles below are what the remediation runner validates locally before a pull request. Runner-only changes use hygiene, runner/probe tests, API/frontend build
health checks and browser health smoke. The bounded auth profile uses auth/session race tests,
API/frontend builds and health/login/registration browsers. The auth-persistence profile adds
real SQLite/MySQL rotation and transaction boundaries, migrations and auth browsers, with
additional MariaDB coverage in CI. It requires all six rotation boundary roots at the candidate;
shared-interface edits also need proof that only the refresh-token interface body changed.
The bounded mailer profile uses SMTP deadline/header/TLS/privacy race tests, focused
password-reset/form/quote/automation delivery callers, API/frontend builds and health smoke; no full frontend
unit suite or unrelated feature browser is selected. Missing or skipped required roots fail.
It changes no database behavior; the migration gates remain part of every full run.
Other shared repository/schema/mixed changes retain full fallback. The bounded transaction-helper profile uses API build/vet, transaction
and caller race regressions, configured migration checks and browser health smoke, with
SQLite/MySQL locally and additional MariaDB boundaries in a full CI run. The existing empty lead-conversion
concurrency placeholder remains a reported gap. `make verify` runs the complete non-browser checks
locally; unfiltered `make e2e` runs the full browser suite. The manual
[Release workflow](../.github/workflows/release.yml) always runs full validation before tagging
and publishing verified artifacts. Production deploys consume those published artifacts.
The bounded migration-workflow profile runs SQL/SQLite migration checks and health smoke; the
two database migration CI jobs feed the required Backend check on a full run. See the [validation and release runbook](VALIDATION_RELEASE.md).
The separate [Database migrations workflow](../.github/workflows/migrations.yml) runs fresh,
populated-upgrade and rollback/reapply SQL regressions on MySQL 8 and MariaDB 10.11, alongside
the SQLite upgrade fixtures, on every full CI run (a release, or a manual run with `full: true`). A pull
request that changes migration code (`migrations/`, `cmd/migrate/`, the workflow or its coverage gate)
runs the MySQL 8 leg alone; it is not a required check. Required roots and their
descendants cannot be skipped; revision-bound JSON artifacts retain the results.
CI also checks the API reference on every change: `scripts/ci/check-api-docs.py` (a Backend-job
step; `make verify-api-docs`, part of `make verify` and of a full CI run, adds the route extractor's
Go tests, which a pull request runs only when it touches the reference's sources) regenerates `api/swagger.json`, `api/swagger.yaml` and the static HTML
reference `api/index.html` and requires them to match the committed files, every routed endpoint
to have an operation (and the reverse) with security matching the route's authentication, every
query parameter, form field and body the handler reads to be documented, every operation,
parameter and property to be described, and the known closed sets to match their Go constants;
see the
[developer guide](DEVELOPMENT.md#api-docs-gate).
CI also publishes documentation impact. New local workflow configurations require explicit
documentation review and verify reviewed document contents after merge; see
[documentation maintenance](DOCUMENTATION_WORKFLOW.md). The CI impact report alone is not
an approval of documentation accuracy.

## How to Read This Document

| Column | Meaning |
|--------|---------|
| **Feature** | What the user can do |
| **Description** | How it works end-to-end |
| **E2E Tests** | Playwright tests that exercise the full stack |
| **Unit Tests** | Go handler/service tests + frontend component tests |
| **Integration Tests** | Go tests that hit a real database (SQLite in-memory) |
| **Status** | `covered` / `partial` / `gap` / `untested` / `unverified` |
| **Known Issues** | Bugs, limitations, missing scenarios |

Status meanings:
- **covered** -- happy path and key edge cases are tested
- **partial** -- happy path tested, but significant scenarios missing
- **gap** -- feature exists but important test coverage is missing
- **untested** -- no automated tests exist
- **unverified** -- the row could not be confirmed from the code; treat the status as unknown

## 4d. Products & Quotes (2026-10)

A product catalogue (name, SKU, integer price in minor units next to an ISO 4217 code, active
flag) and quotes that belong to a customer and/or a deal. A quote has lines (a product, a quantity,
a per-line discount and a per-line tax rate in basis points); the line copies the product's name and
price when it is added, and the line totals, line tax and the quote's net, tax and gross totals are
computed on the server with round-half-up (#324: tax per line, then summed; the 10^12 cap is on the
gross total; `total_cents` stays net). Since #343 a line quantity is an exact decimal from 0.001 to
1,000,000 with at most three decimal places (stored as thousandths, sent and returned as a JSON
number such as `1.5`); the line total is unit price × quantity after the discount, rounded half up
once without floating point, the subtotal sums the rounded line gross values, and the email prints
the quantity without trailing zeros (4d.11). Every quote
moves through `draft → sent → accepted | rejected | expired`, with `sent → draft` to revise; each
move is claimed by a conditional update and writes a status-history row in the same transaction,
and only a draft is editable. Quotes use the deal role guard (admin and sales; sales sees only the
quotes it owns, narrowed inside the query). A sent or accepted quote can be emailed as a plaintext
rendering to the linked customer's current address; since #384 the printable document is attached
as a PDF when PDF output is on (`QUOTE_PDF_CHROME_PATH`, 4d.14) and the mail stays text only when
it is off or the render fails. The mail goes out
with a subject naming the configured product (`general.company_name`, else `GopherCRM`, #292);
the mailer refuses CR/LF in headers. Quotes copy no contact data; their
staff-typed title, notes and line descriptions are redacted when the quote's customer, or the
customer or lead of its deal, is erased, whatever the status (#245: title `[redacted]`, notes
empty, each line's description its product's name; status, totals and history stay). Since #382 the email of a sent
quote ends with a single-use client response link (`APP_BASE_URL/quote-response?token=...`, only
the token's hash stored), answered by the unauthenticated `GET` and `POST /quotes/public/response`:
the client sees the quote and accepts or declines it, which moves it to accepted or rejected with
one history row in one transaction (4d.12). Since #383 the link opens the public SPA page
`/quote-response`, which shows the quote and records the answer without an account (4d.13). Decided for this release: accepting a quote does
not change its deal; expiry is manual (acceptance is refused after `valid_until`); support cannot
read quotes; sending is refused when the quote has no live customer. The frontend slice (4d.9,
2026-10-28, issue #167) adds the `/products` list and admin-only form, the `/quotes` list with its
create dialog, the `/quotes/{id}` detail with draft-only line editing, the valid-transition status
buttons, the email confirmation and the status history, the `/quotes/{id}/print` print layout,
the DealDetail "Quotes" section and the admin/sales-only navigation entries and routes. Money is
shown from the server's integer minor units with the quote's currency, discounts are typed as
percentages and sent as basis points, and the totals are always the server's. Since #325 the line
dialog also edits each line's tax rate (a percentage sent as `tax_rate_bp`), and the detail and
print pages show each line's tax rate and tax and the net, tax and gross totals from the server;
the quotes list and the deal's Quotes section still show the net total. Since #346 the line dialog
takes fractional quantities (0.001 to 1,000,000, at most three decimals, a dot as the only decimal
separator) and shows the API's `error.details.quantity` on the Quantity field, and the detail and
print pages show quantities without trailing zeros (4d.11). The public `/quote-response` page
(4d.13, #383) is the one quote screen outside the application shell: it is reached without a
session and calls the API through `publicApi`, which sends no bearer token. Catalog cases in
`docs/testing/15-products-quotes.md`; API contract in `api/swagger.yaml` under `/products` and
`/quotes`.

or a daily UTC schedule and run ordered
steps (`wait`, `condition`, `create_task`, `assign_owner`, `send_email` to a staff user, `notify`)

commits it; a worker (on any number of replicas sharing one MySQL/MariaDB database, #237) turns

locking read of the record and an owner-fenced conditional advance of the run row, parks waits in
`resume_at`, continues schedule passes from a persisted cursor and recovers runs whose lease went

## 10b. 2026-08 Backend Build-out (session lifecycle, analytics, export/assign, API-key management)

Added after this matrix was first compiled; every row verified by the named suites. See
CHANGELOG "Added" for the full behavioural description.

| Feature | Endpoints | Tests |
|---|---|---|
| Auth sessions | `POST /auth/refresh`, `/auth/logout`, `/auth/change-password`, `/auth/password-reset`, `/auth/password-reset/confirm`; login returns a rotating refresh token. Reset confirmation is one transaction: conditional token claim, locking owner re-check, password and lockout update, revocation of every refresh token (#102). Refresh rotation is one transaction too: locking owner re-check, conditional single-use claim of the presented token, successor insert and JWT signing, with a committed containment revocation for a dead owner (#103). Password change is one transaction that renews the presenting session and revokes the others (#116). The bounded AEO runtime validation profile selects startup, service, provider, persistence
and transaction regressions with health/provider browsers. It requires committed startup
and interface scope proofs and six lifecycle roots; this policy does not itself deliver
the queued runtime fix. Optional candidate inspection stops the runner before checks until
the operator records the exact plan. See [validation](VALIDATION_RELEASE.md) and
[operations](../automation/langflow/OPERATIONS.md).

Comment-only changes to the root `.env.example` can accompany these bounded profiles
when the shared committed proof preserves every active setting. Unsupported syntax and
actual setting changes retain full fallback; explicit full/release gates are unchanged.
