# User Management — Test Cases

Playwright end-to-end cases for the admin Users area (`/users`, `/users/new`, `/users/:id`,
`/users/:id/edit`) and for the "My Profile" entry under Settings. The whole `/users` route subtree is
admin-only on the frontend (pathless `ProtectedRoute` layout routes asking for `users.view`,
`users.create` and `users.update`, which only the admin system role holds) and the
list/create/delete handlers are admin-only on the backend (`middleware.RequireRole`), so this area
plus the `create-admin` CLI are the only ways an elevated role can ever be issued. Every case below
states the behaviour the code exhibits today; where that behaviour is broken or surprising the
Expected field still describes it and a **Known issue** line records the defect.

**Constraints**

- All test data comes from `generateUserData()` in `gocrm-ui/e2e/fixtures/admin-user.ts`. Never
  hardcode an email address; the seeded admin (`testAdminCredentials`) is the only fixed account
  and it must never be deleted.
- Deleting a user is an irreversible GDPR Article 17 erasure (`internal/repository/erasure.go`):
  personal fields are overwritten in place, API keys and refresh tokens are purged, then the row is
  soft-deleted. Erasing a customer-role login also redacts the deal and quote text of the
  customers and leads it reaches (#245); erasing a staff user leaves the deals and quotes it owns
  untouched. **Only ever delete a user the test itself created**, and only in the cases that
  explicitly say so.
- Cases that log in as a non-admin need a login helper for arbitrary credentials. `LoginPage`
  (`gocrm-ui/e2e/pages/login.page.ts`) can already do it; `AdminAuthHelper` cannot, because
  it only logs in the seeded admin (`testAdminCredentials`). Building that helper is a
  prerequisite for the RBAC cases marked *planned*.
- The password generated by `generateUserData()` is `TempPass123!` (12 chars, meets the backend's
  `min=10` plus complexity rules).

### TC-USER-006 — Pin the pagination footer to the current page size
- **Priority:** P1
- **Type:** regression
- **Preconditions:** Admin logged in; more users exist than one page holds (the shared dev database
  currently returns `meta.total` in the high tens).
- **Steps:**
  1. Open `/users` with the default page size of 10.
  2. Read the `TablePagination` label and the state of the "next page" button.
  3. Change rows per page to 25 and repeat.
- **Expected:** The footer reads "1–10 of 10" and the next-page button is disabled even though the
  response envelope carries `meta.total` far greater than 10. `usersApi.getUsers` sets
  `total = users.length` because the axios interceptor has already unwrapped `{success,data}` to a
  bare array and `meta` is discarded, so `totalCount` is only ever the current page length. Raising
  rows per page to 25 issues `GET /users?page=1&limit=25` and shows 25 rows with the same
  page-length total. Pages beyond the first are unreachable from the footer; sorting or searching is
  the only way to bring an older account into view.
- **Known issue:** The list endpoint returns correct pagination metadata (`meta.total`,
  `meta.total_pages`) and the frontend drops it. Related to the "user handler returns just the array
  at data level" comment in `gocrm-ui/src/api/endpoints/users.ts`.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

## 7.6 Search users

### TC-USER-009 — Search users by email, first name and last name
- **Priority:** P1
- **Type:** functional
- **Preconditions:** Admin logged in; a user created in-test with `generateUserData()`.
- **Steps:**
  1. Open `/users`.
  2. Type the created user's email into the "Search users..." field.
  3. Repeat with the first name, then the last name.
- **Expected:** Each keystroke issues `GET /users?page=1&limit=10&search=<term>`; the search is
  server-side (`UserHandler.List` → `userService.Search`) and matches email, first name and last
  name. The table narrows to the matching row. There is no debounce — a ten-character term fires ten
  requests, which counts against the 120 req/min moderate rate limit.
- **Automation:** automated — `gocrm-ui/e2e/tests/admin-users.spec.ts` "admin can search users"
  (since 2026-09-23 it asserts that the search returns exactly the user it created).

## 7.7 Sort users

### TC-USER-011 — Sort by Created and by Username
- **Priority:** P1
- **Type:** functional
- **Preconditions:** Admin logged in; two users created in-test.
- **Steps:**
  1. Open `/users`.
  2. Click the "Created" column header until the backend receives `sort_order=desc`.
  3. Click the "Username" column header.
- **Expected:** Step 2 issues `GET /users?sort_by=created_at&sort_order=asc|desc` and the freshly
  created users appear at the top once `desc` is in effect. Step 3 issues
  `sort_by=email` — `UserList.handleSort` maps the `username` column id onto `email`, which is one of
  the six columns the handler allows (`created_at, updated_at, email, first_name, last_name, role`).
  Note that each sort refetch briefly unmounts the table (`Loading` replaces it), which resets
  `DataTable`'s internal sort state, so a fixed number of clicks cannot be relied on to reach `desc`.
- **Automation:** automated — `gocrm-ui/e2e/screenshots/07-users.spec.ts` "01-list" (its
  `sortByNewest` helper clicks until `sort_order=desc` is observed on the wire)

### TC-USER-012 — Record the header clicks the backend ignores
- **Priority:** P2
- **Type:** regression
- **Preconditions:** Admin logged in; the list currently sorted by Created desc.
- **Steps:**
  1. Click the "Status" column header.
  2. Click the "Name" column header.
- **Expected:** Step 1 sends `sort_by=is_active`, step 2 sends `sort_by=name`. Neither value is in

- **Known issue:** FEATURES.md row 7.7 records the missing E2E coverage; the header/allowlist

### TC-USER-020 — Submit a nine-character password that the client accepts
- **Priority:** P1
- **Type:** validation
- **Preconditions:** Admin logged in.
- **Steps:**
  1. Open `/users/new`, fill a `generateUserData()` payload but use the password `Abcdefg1!` in both
     password fields.
  2. Submit.
- **Expected:** The client-side schema passes (it only requires 8 characters), the request is sent,
  and `POST /users` returns 400 with `error.code = VALIDATION_ERROR`, `error.message = "Validation
  failed"` and `error.details.Password = "Password must be at least 10 characters long"` (the
  `binding:"min=10"` tag routed through the error-handler middleware). The snackbar shows only
  "Validation failed" — the per-field detail is not surfaced. The form stays on `/users/new` with
  the entered values intact and no account is created.
- **Known issue:** Client schema (`min 8`) and server binding (`min=10`) disagree, so a password
  between 8 and 9 characters produces a server round-trip and an unhelpful message. The real rules
  live in `internal/utils/password.go`: at least 10 characters plus one upper-case letter, one
  lower-case letter, one digit and one special character.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

### TC-USER-043 — Reject a password longer than 72 bytes
- **Priority:** P1
- **Type:** validation
- **Preconditions:** Admin bearer token.
- **Steps:**
  1. `POST /users` with a valid body whose password is policy-compliant and 73 bytes long
     (`Aa1!` followed by 69 `x`).
  2. Repeat with `Aa1!` followed by 35 `é` (39 characters, 74 bytes).
  3. Repeat with a 72-byte password (`Aa1!` followed by 68 `x`).
- **Expected:** Steps 1 and 2 return **400** with `error.code = BAD_REQUEST` and
  `error.message = "password must be at most 72 bytes long"`; the length is counted in bytes and
  checked in the handler before the complexity policy and before the service is called, so no
  account is created. A password that is both weak and over 72 bytes gets the same length
  message. Step 3 returns **201**. `POST /auth/register`, `POST /auth/change-password` and
  `POST /auth/password-reset/confirm` give the identical answer (see TC-AUTH-037a for the reset
  link, which is not spent). `PUT /users/<id>` ignores a `password` key and `PUT /users/me`
  refuses one with `PASSWORD_FIELD_NOT_ACCEPTED`, so neither has a length answer. The SPA forms
  set no upper bound and show the server message.
- **Automation:** automated — `internal/handler/auth_password_length_test.go`
  `TestPasswordLengthLimit` (the four routes, mocked services), `internal/utils/password_test.go`
  `TestValidateNewPassword`, and the control subtest of `tests/auth_user_write_errors_test.go`
  `TestUserWriteFailureIsInternalError` (real stack: 72 bytes stored, 73 refused, row count
  unchanged). No browser case.

### TC-USER-044 — A user that cannot be stored is a 500 without the database error

- **Automation:** automated — `tests/auth_user_write_errors_test.go`

### TC-USER-024 — Edit a user's name
- **Priority:** P1
- **Type:** functional
- **Preconditions:** Admin logged in; a user created in-test.
- **Steps:**
  1. Open `/users`, search for the user, click the pencil icon.
  2. Replace First Name and Last Name.
  3. Click "Update User".
- **Expected:** The edit form is pre-filled from `GET /users/<id>` and shows **no** password fields.
  `PUT /users/<id>` returns 200, the snackbar reads "User updated successfully" and the app
  navigates to `/users` where the row shows the new name. The one password field the edit form can
  show is "Current password", and only while the signed-in user changes the email of its own
  account (#394, TC-USER-047); editing another user never shows it.
- **Automation:** automated — `gocrm-ui/e2e/tests/admin-users.spec.ts` "admin can edit an existing
  user" (since 2026-09-23 it edits only its own user, found by email, and asserts the new name; it
  used to edit row 1, possibly a real account)

### TC-USER-025 — Change another user's role
- **Priority:** P0
- **Type:** functional
- **Preconditions:** Admin logged in; a `customer` user created in-test.
- **Steps:**
  1. Open `/users/<id>/edit`.
  2. Change the Role select from Customer to Sales.
  3. Submit.
- **Expected:** `PUT /users/<id>` carries `role: "sales"` and returns 200; the handler applies `role`
  only because the caller's role is admin (it silently drops `role` and `is_active` for anyone
  else). The list row shows the Sales chip. On the user's next request the auth middleware reads the
  role from the database, so the change takes effect immediately without re-login. Since #381 the
  option list comes from `GET /roles`: a system role's option value is its key (`sales`), a custom
  role's is `custom:<id>` (see TC-USER-041); a system role is sent without a `role_id` key.
- **Automation:** automated — `gocrm-ui/e2e/tests/admin-users.spec.ts` "admin can manage user
  permissions through roles" (since 2026-09-23 it changes only its own user's role and asserts
  `sales` is shown; it used to promote whichever user was in row 1)

### TC-USER-026 — Demote your own admin account
- **Priority:** P0
- **Type:** negative
- **Preconditions:** A **second** admin created in-test (TC-USER-016) and logged in. Never run this
  against the seeded `test-admin@gocrm.test` account — it would break every other spec.
- **Steps:**
  1. As that admin, open `/users/<own id>/edit`.
  2. Change Role from Admin to Customer and submit.
  3. Reload the page and navigate to `/users`.
- **Expected:** `PUT /users/<own id>` returns 200 — nothing in `UserHandler.Update` prevents an admin
  from demoting themselves. The snackbar reads "User updated successfully" and the app returns to

  database on every request. After a reload, `GET /users/me` returns `role: "customer"`, the drawer
  loses its Users entry and `/users` redirects to `/unauthorized`. The account cannot restore itself
  — only another admin or the `create-admin` CLI can.
- **Known issue:** An admin can still demote itself here while another active admin remains (the
  case's precondition); `POST /users/{id}/deactivate` refuses the caller's own account, this route
  does not (`docs/DEVELOPMENT.md`, "Defects found while documenting the API"). The last active
  admin is protected since #348: the same request answers 409 `LAST_ADMIN` and writes nothing. Since #381 the form stays open on that answer and shows
  "The last active administrator cannot be given another role or be deactivated." above its
  buttons instead of only a snackbar (Vitest `src/pages/users/UserForm.roles.test.tsx`).
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended; needs the login
  helper for arbitrary credentials)

### TC-USER-027 — Deactivate a user with the Active Account switch
- **Priority:** P0
- **Type:** functional
- **Preconditions:** Admin logged in; a `sales` user created in-test whose credentials are known.
- **Steps:**
  1. Log in as that user in a second browser context and keep the tab open.
  2. As the admin, open `/users/<id>/edit`, turn the "Active Account" switch off and submit.
  3. Back in the first context, reload and try an action; then log out and try to log in again.
- **Expected:** `PUT /users/<id>` carries `is_active: false` and returns 200; the list and detail

  touched. A **new** login attempt returns 401 with the same generic "invalid credentials" message

  on every authenticated request, so previously-issued access tokens return 401 Unauthorized as soon as the
  account is deactivated. Since #526 the same transaction also increments `token_version`, revokes
  every refresh token and revokes every API key of the account.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

### TC-USER-034 — Reuse the email address of an erased user
- **Priority:** P0
- **Type:** functional
- **Preconditions:** The user deleted in TC-USER-033; its email string retained by the test.
- **Steps:**
  1. Open `/users/new`.
  2. Fill a fresh payload but reuse the erased user's email address.
  3. Submit.
- **Expected:** `POST /users` returns **201**, not 409. The unique index on `email` covers
  soft-deleted rows too, so reuse only works because erasure replaced the address — this is the
  behaviour that makes a composite `UNIQUE(email, deleted_at)` index unnecessary, and wrong: MySQL
  and SQLite both treat NULLs in a unique index as distinct, so live rows (`deleted_at IS NULL`)
  would then allow unlimited duplicate live emails. The new account is unrelated to the erased one
  and gets a new id.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

## 7.9 My Profile

### TC-USER-038 — Open Settings → Profile
- **Priority:** P1
- **Type:** functional
- **Preconditions:** Logged in as any role.
- **Steps:**
  1. Expand "Settings" in the drawer and click "Profile" (or navigate to `/settings/profile`).
  2. Read the "Account details" card and the "Change password" form.
- **Expected:** `gocrm-ui/src/pages/settings/Profile.tsx` renders an `h4` reading "Profile", then
  two sections. "Account details" shows the signed-in user's name, email, role and member-since date
  read-only, from `AuthContext`: the page makes no `GET /users/me` request of its own (the app calls
  it from `authApi.getCurrentUser` to populate the context). "Change password" asks for the current,
  new and confirmation passwords and submits to `POST /auth/change-password` (TC-AUTH-038). The page
  has no form for editing the email or the names. The backend's `PUT /users/me` — which accepts
  email, first name and last name, refuses any body carrying `password` or `new_password` with 400
  `PASSWORD_FIELD_NOT_ACCEPTED` (#254) and changes the email only with the account's
  `current_password` (#394, TC-USER-045 to TC-USER-049; both backend-automated in
  `tests/users_me_password_test.go`) — has no caller anywhere in the frontend. The route is
  deliberately outside the admin-guarded layout route, so every role can reach the page.
- **Known issue:** There is no profile-edit UI, so `PUT /users/me` has no browser coverage;
  FEATURES.md row 7.9 stays partial for that reason.
- **Automation:** automated for the page — `gocrm-ui/e2e/tests/settings.spec.ts` "shows the signed-in
  account details" (as the seeded admin), "changes the password and the new one works on the next
  login" and "rejects a wrong current password with the server message" (as a registered customer),
  and Vitest `src/pages/settings/Profile.test.tsx`. Sales and support are not driven through this
  page by these specs. `PUT /users/me` is backend-automated only.
