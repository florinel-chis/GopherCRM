# User Management — Test Cases

Playwright end-to-end cases for the admin Users area (`/users`, `/users/new`, `/users/:id`,
`/users/:id/edit`) and for the "My Profile" entry under Settings. The whole `/users` route subtree is
admin-only on the frontend (a pathless `ProtectedRoute requiredRole="admin"` layout route) and the
list/create/delete handlers are admin-only on the backend (`middleware.RequireRole`), so this area
plus the `create-admin` CLI are the only ways an elevated role can ever be issued. Every case below
states the behaviour the code exhibits today; where that behaviour is broken or surprising the
Expected field still describes it and a **Known issue** line records the defect.

**Sources consulted**

  `gocrm-ui/src/api/client.ts`, `gocrm-ui/src/types/index.ts`

**Constraints**

- All test data comes from `generateUserData()` / `generateAdminUser()` in
  `gocrm-ui/e2e/fixtures/admin-user.ts`. Never hardcode an email address; the seeded admin
  (`testAdminCredentials`) is the only fixed account and it must never be deleted.
- Deleting a user is an irreversible GDPR Article 17 erasure (`internal/repository/erasure.go`):
  personal fields are overwritten in place, API keys and refresh tokens are purged, then the row is
  soft-deleted. **Only ever delete a user the test itself created**, and only in the cases that
  explicitly say so.
- Cases that log in as a non-admin need a login helper for arbitrary credentials. `LoginPage`
  (`gocrm-ui/e2e/pages/login.page.ts`) can already do it; `AdminAuthHelper` cannot, because
  `loginExistingAdmin` asserts the admin flow. Building that helper is a prerequisite for the RBAC
  cases marked *planned*.
- The password generated by `generateUserData()` is `TempPass123!` (12 chars, meets the backend's
  `min=10` plus complexity rules).

## 7.1 View users list

### TC-USER-001 — Show the users list to an admin
- **Priority:** P0
- **Type:** functional
- **Preconditions:** Logged in as the seeded admin via `AdminAuthHelper.ensureAdminLoggedIn()`.
- **Steps:**
  1. Navigate to `/users`.
  2. Wait for the `h4` "Users" heading.

### TC-USER-004 — Confirm the API guard is narrower than the UI guard

### TC-USER-006 — Pin the pagination footer to the current page size
- **Priority:** P1
- **Type:** regression
- **Preconditions:** Admin logged in; more users exist than one page holds (the shared dev database
  currently returns `meta.total` in the high tens).
- **Steps:**
  1. Open `/users` with the default page size of 10.
  2. Read the `TablePagination` label and the state of the "next page" button.
  3. Change rows per page to 25 and repeat.
- **Expected:** The footer reads "1–10 of 10" and the next-page button is disabled even though the
  response envelope carries `meta.total` far greater than 10. `usersApi.getUsers` sets
  `total = users.length` because the axios interceptor has already unwrapped `{success,data}` to a
  bare array and `meta` is discarded, so `totalCount` is only ever the current page length. Raising
  rows per page to 25 issues `GET /users?page=1&limit=25` and shows 25 rows with the same
  page-length total. Pages beyond the first are unreachable from the footer; sorting or searching is
  the only way to bring an older account into view.
- **Known issue:** The list endpoint returns correct pagination metadata (`meta.total`,
  `meta.total_pages`) and the frontend drops it. Related to the "user handler returns just the array
  at data level" comment in `gocrm-ui/src/api/endpoints/users.ts`.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

## 7.6 Search users

### TC-USER-009 — Search users by email, first name and last name
- **Priority:** P1
- **Type:** functional
- **Preconditions:** Admin logged in; a user created in-test with `generateUserData()`.
- **Steps:**
  1. Open `/users`.
  2. Type the created user's email into the "Search users..." field.
  3. Repeat with the first name, then the last name.

  (the existing test types a term and waits, but asserts nothing about the result; extend it to
  assert the row).

## 7.7 Sort users

### TC-USER-011 — Sort by Created and by Username
- **Priority:** P1
- **Type:** functional
- **Preconditions:** Admin logged in; two users created in-test.
- **Steps:**
  1. Open `/users`.
  2. Click the "Created" column header until the backend receives `sort_order=desc`.
  3. Click the "Username" column header.
- **Expected:** Step 2 issues `GET /users?sort_by=created_at&sort_order=asc|desc` and the freshly
  created users appear at the top once `desc` is in effect. Step 3 issues
  `sort_by=email` — `UserList.handleSort` maps the `username` column id onto `email`, which is one of
  the six columns the handler allows (`created_at, updated_at, email, first_name, last_name, role`).
  Note that each sort refetch briefly unmounts the table (`Loading` replaces it), which resets
  `DataTable`'s internal sort state, so a fixed number of clicks cannot be relied on to reach `desc`.
- **Automation:** automated — `gocrm-ui/e2e/screenshots/07-users.spec.ts` "01-list" (its
  `sortByNewest` helper clicks until `sort_order=desc` is observed on the wire)

### TC-USER-012 — Record the header clicks the backend ignores
- **Priority:** P2
- **Type:** regression
- **Preconditions:** Admin logged in; the list currently sorted by Created desc.
- **Steps:**
  1. Click the "Status" column header.
  2. Click the "Name" column header.
- **Expected:** Step 1 sends `sort_by=is_active`, step 2 sends `sort_by=name`. Neither value is in
  the handler's allowlist, so `sortBy` is blanked and the response falls back to the default
  unsorted listing — the visible order changes (the previous Created-desc ordering is lost) but is
  not sorted by the clicked column. The header still paints its sort arrow, so the UI claims a sort
  that did not happen.
- **Known issue:** FEATURES.md row 7.7 records the missing E2E coverage; the header/allowlist
  mismatch is not recorded anywhere.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

## 7.8 Filter by role and status

### TC-USER-013 — Record that the Role dropdown does not filter
- **Priority:** P1
- **Type:** regression
- **Preconditions:** Admin logged in; at least one user of each of two different roles on the first
  page (create a `sales` user in-test to guarantee it).
- **Steps:**
  1. Open `/users`.
  2. Open the "Role" select and choose "Sales".
  3. Compare the rows before and after.
- **Expected:** The selection issues `GET /users?page=1&limit=10&role=sales`. The backend ignores the
  `role` parameter entirely (`UserHandler.List` reads only `page`, `offset`, `limit`, `sort_by`,

  page-local filtering would also be wrong.

  the current page; in the code it is applied nowhere at all. The existing E2E test only asserts
  `count >= 1`, which passes whether or not the filter works.
- **Automation:** automated — `gocrm-ui/e2e/tests/admin-users.spec.ts` "admin can filter users by
  role" (extend it to assert the no-op explicitly)

### TC-USER-020 — Submit a nine-character password that the client accepts
- **Priority:** P1
- **Type:** validation
- **Preconditions:** Admin logged in.
- **Steps:**
  1. Open `/users/new`, fill a `generateUserData()` payload but use the password `Abcdefg1!` in both
     password fields.
  2. Submit.
- **Expected:** The client-side schema passes (it only requires 8 characters), the request is sent,
  and `POST /users` returns 400 with `error.code = VALIDATION_ERROR`, `error.message = "Validation
  failed"` and `error.details.Password = "Password must be at least 10 characters long"` (the
  `binding:"min=10"` tag routed through the error-handler middleware). The snackbar shows only
  "Validation failed" — the per-field detail is not surfaced. The form stays on `/users/new` with
  the entered values intact and no account is created.
- **Known issue:** Client schema (`min 8`) and server binding (`min=10`) disagree, so a password
  between 8 and 9 characters produces a server round-trip and an unhelpful message. The real rules
  live in `internal/utils/password.go`: at least 10 characters plus one upper-case letter, one
  lower-case letter, one digit and one special character.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)

### TC-USER-021 — Submit a long password that fails the complexity rules

### TC-USER-025 — Change another user's role

  2. Change the Role select from Customer to Sales.
  3. Submit.

### TC-USER-026 — Demote your own admin account
- **Priority:** P0
- **Type:** negative
- **Preconditions:** A **second** admin created in-test (TC-USER-016) and logged in. Never run this
  against the seeded `test-admin@gocrm.test` account — it would break every other spec.
- **Steps:**
  1. As that admin, open `/users/<own id>/edit`.
  2. Change Role from Admin to Customer and submit.
  3. Reload the page and navigate to `/users`.
- **Expected:** `PUT /users/<own id>` returns 200 — nothing in `UserHandler.Update` prevents an admin
  from demoting themselves. The snackbar reads "User updated successfully" and the app returns to
  `/users`, which still renders because `AuthContext` still holds the cached admin user; the very
  next `GET /users` however returns **403**, since `middleware.Auth` re-reads the role from the
  database on every request. After a reload, `GET /users/me` returns `role: "customer"`, the drawer
  loses its Users entry and `/users` redirects to `/unauthorized`. The account cannot restore itself
  — only another admin or the `create-admin` CLI can.
- **Known issue:** Self-demotion is unguarded and can lock the last admin out of user management. Not
  currently recorded in FEATURES.md or ROADMAP.md.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended; needs the login
  helper for arbitrary credentials)

### TC-USER-027 — Deactivate a user with the Active Account switch
- **Priority:** P0
- **Type:** functional
- **Preconditions:** Admin logged in; a `sales` user created in-test whose credentials are known.
- **Steps:**
  1. Log in as that user in a second browser context and keep the tab open.
  2. As the admin, open `/users/<id>/edit`, turn the "Active Account" switch off and submit.
  3. Back in the first context, reload and try an action; then log out and try to log in again.
- **Expected:** `PUT /users/<id>` carries `is_active: false` and returns 200; the list and detail
  pages show the grey "Inactive" chip. This is the reversible suspension — no personal data is
  touched. A **new** login attempt returns 401 with the same generic "invalid credentials" message
  as a wrong password (deliberate anti-enumeration), and `POST /auth/refresh` for that account is

### TC-USER-034 — Reuse the email address of an erased user
- **Priority:** P0
- **Type:** functional
- **Preconditions:** The user deleted in TC-USER-033; its email string retained by the test.
- **Steps:**
  1. Open `/users/new`.
  2. Fill a fresh payload but reuse the erased user's email address.
  3. Submit.
- **Expected:** `POST /users` returns **201**, not 409. The unique index on `email` covers
  soft-deleted rows too, so reuse only works because erasure replaced the address — this is the
  behaviour that makes a composite `UNIQUE(email, deleted_at)` index unnecessary, and wrong: MySQL
  and SQLite both treat NULLs in a unique index as distinct, so live rows (`deleted_at IS NULL`)
  would then allow unlimited duplicate live emails. The new account is unrelated to the erased one
  and gets a new id.
- **Automation:** planned — `gocrm-ui/e2e/tests/admin-users.spec.ts` (extended)
